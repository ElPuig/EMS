# What's new:

## Working-schedule import wizard simplified (no more per-teacher file upload, no more silent auto-archiving):
- Removed the per-employee scoped file upload (`teacher_id`/`file` fields, the Schedule tab's "Import" button) — a teacher joining mid-year now gets their schedule via the tab's own existing "New" panel (blank framework or copy from another teacher) or by hand, never a single-file XML upload. The batch importer (`attachment_ids`, the "Working Schedules" list's cog menu) is the only way in.
- A conflicting active session found during import (same space/day/time, different subject or group) is no longer silently archived: it now **blocks** the import with a clear error naming the conflicting session, in both the onchange preview and `create()`. Legitimate co-teaching (same subject, sharing a group) is left alone and surfaced as a non-blocking confirmation banner instead.
- This was possible because groups are permanent and reused across academic years (confirmed via `353-add-course-transition-wizard-setup-next-course`, merged in this branch) — the course transition wizard archives a study's outgoing attendance templates before its groups are ever reimported, so a fresh import genuinely never writes on top of already-populated data for its own scope; any active overlap it finds is always either co-teaching or a real problem, never something to guess-and-archive.
- `ems.attendance_template.find_external_conflicts` renamed to `classify_external_conflicts`, now returning `(co_teaching, space_conflicts)` instead of a single recordset to silently archive.
- Found while verifying the redesign against the real, incremental (department-by-department) import workflow: reusing the Schedule tab's own `sync_from_schedule_batch`/`_reconcile_teacher_groups` for the batch importer silently archived a shared teacher's already-imported *other* department schedule the moment a second department's file mentioned that same teacher again — zero error, pure data loss. Fixed with a dedicated `_reconcile_fresh_import`/`sync_from_schedule_batch_fresh_import` write path (no pre-scan of a submitting teacher's untouched other combos) and `ems.teaching.sync_from_schedule(..., replace=False)` for the importer's own call — the Schedule tab's live-editor methods are untouched.
- New `ems.attendance_template.find_self_conflicts`: a teacher imported in this same batch, double-booked against their own already-active schedule for a genuinely different subject/group (e.g. two departments' files scheduling them at the same time), now surfaces as its own named blocking banner/error in the wizard, instead of falling through to Odoo's raw, unworded `check_overlap` constraint error.
- See `docs/en/developers/employees/working_schedule.md` for the full design; `plans/working_schedule_import_redesign.md` tracks what's left (a group/teacher correction dropdown for unresolved codes is designed but not yet implemented).

## Working-schedule import wizard becomes a guided, multi-step flow (skeleton + first screen):
- The single-screen wizard is being rebuilt into a 7-step guided flow (a statusbar showing Welcome → Resolve groups → Resolve teachers → Internal conflicts → Existing schedule conflicts → Pending teachers → Existing teachers), so each class of problem gets its own screen instead of a wall of banners all at once. **Only the first screen ("Welcome", file upload) has real behavior in this pass** - the middle 5 steps are placeholders that just advance the statusbar for now (their own resolution screens are separate, not-yet-built work - see `plans/working_schedule_import_redesign.md`); the final step's "Import" button already does the real work, unchanged in spirit from before.
- Nothing is written to any model until the final "Import" click: leaving the Welcome screen parses every attached file and caches the result - the actual `resource.calendar`/`ems.teaching`/`ems.attendance_template` writes only happen once the flow reaches the last step.
- `create()` is back to a plain, un-overridden default - previously it did the entire import as a side effect of the wizard's very first save, which would have made the *first* "Continue" click on the new intro screen perform the whole import prematurely.
- Found and fixed a real Odoo gotcha along the way: a `type="object"` button whose method returns nothing gets silently converted into "close the window" by the web client - which closed this wizard's dialog the moment the very first "Continue" click saved the record. Fixed by having the button's handler always return an explicit action re-opening the same wizard record.
- **Welcome screen simplified to just the file upload, no validation at all (developer feedback right after trying it):** the first version of this screen still showed the old wizard's four banners (unknown e-mail, unresolved group/subject, missing classroom and room conflicts in red; pending-identification codes in blue; already-has-a-schedule/co-teaching in yellow), live-updated via an onchange as files were attached - but resolving those problems is exactly what steps 2-3 are meant to do, so surfacing (or blocking on) them here pre-empted those screens' own purpose. Now "Continue" activates the moment any file is attached, full stop; every real problem is deferred all the way to the final "Import" click instead (today, since steps 2-6 aren't built yet, that's where it surfaces - an unresolved e-mail during this pass's testing showed as a plain error dialog at Import time rather than as a banner on the welcome screen). The one exception: an unresolvable subject/group *code* still blocks leaving the welcome screen, since parsing that row produces no data at all to defer.
- **Continue/Import/Cancel moved from the arch's `<header>` to a `<footer>` (developer feedback: they were showing up alongside Odoo's own generic Save/Discard, not in their place):** the wizard's `<header>` only had the `state` statusbar field to begin with, but its 3 action buttons were also declared there - since a `target="new"` dialog with no `<footer>` in its arch falls back to Odoo's own generic Save/Discard/Remove buttons in the modal's actual footer area (`web.FormView`'s `layout-buttons` slot, portaled straight into `.modal-footer`), that generic row kept showing up alongside our own statusbar buttons instead of being replaced by them. Moving the 3 buttons into a real `<footer>` (keeping only the `state` field in `<header>`) makes Odoo use ours instead of the fallback, matching how every other wizard in this codebase already does it (e.g. `ems.grade_import_wizard`). An earlier attempt at this same complaint incorrectly targeted `web.FormStatusIndicator` (a *different*, unrelated "unsaved changes" control-panel icon that isn't even what was rendering here) - reverted once testing showed it changed nothing.
- **Screen 2 ("Resolve groups") is now real, the second of the 7 steps to get actual logic:** an unrecognized `<Students>` name in an uploaded file no longer blocks the Welcome screen - it's deferred to this new step instead, one line per distinct unresolved name (the same typo appearing many times across the batch is one correction, not one per occurrence), each with a dropdown to pick the real group (creating one on the spot is allowed, same as any other group field). A batch with nothing to resolve just shows a confirmation message instead of a list. This required a genuine design decision, checked with the developer first rather than assumed: the Welcome-screen redesign above had left a comment saying an unresolved group "has no later step (yet) that could resolve it" - several already-passing tests took that as a permanent rule, when it was actually only true until this exact screen got built. Confirmed with the developer, then adapted those tests to the new, deferred behavior instead of leaving the screen unbuilt. Subject *codes* are unaffected by this change - still no resolution screen for those, still block at Welcome, same as before.
- User docs (`docs/{en,ca,es}/admin/working-schedules.md`) rewritten to match the current wizard end to end (Welcome → Resolve groups → placeholder steps → Import) and to drop the old per-teacher import instructions, which no longer exist (removed by the batch-only change earlier in this same changelog) - these sections had gone stale across this branch's earlier phases and were never caught until now.
- **"Continue" now renders enabled/disabled instead of appearing/disappearing (developer feedback: "que no te deje continuar hasta que no se hayan seleccionado grupos... creo que quedará más claro si los botones de continuar aparecen como enabled o disabled"):** a "Resolve groups" screen with an unpicked group now shows "Continue" grayed out (not clickable) rather than blocking only after the click, and rather than hiding the button outright the way the Welcome screen used to. Since Odoo's own buttons have no native per-record "disabled" expression, this is built from two buttons sharing the same visual spot - the real one and a cosmetic, always-disabled twin - only one of which is ever actually present, toggled by a new computed `continue_disabled`. Verified in a real browser tour, not just reasoned about: asserts the disabled twin is actually there before a group is picked, and the real one right after.
- **Screen 3 ("Resolve teachers") is now real, the third of the 7 steps to get actual logic:** an unrecognized teacher e-mail no longer waits until the final Import click to fail - it's deferred to this new step instead, one line per distinct unresolved e-mail, each with a dropdown to pick the real teacher (creating a brand-new one is deliberately **not** allowed here - that's still only ever automatic, for a not-yet-hired post code, at the final Import step). A batch with nothing to resolve just shows a confirmation message instead of a list, same "Continue" enabled/disabled behavior as the groups screen. Unlike screen 2, this one needed no developer check-in first - the plan already fully specified this exact behavior, so building it was an unambiguous, intended consequence: the existing "unknown teacher" tour and test were adapted the same way screen 2's were, since an unknown e-mail now surfaces here instead of as an error dialog at Import.
- **Screen 4 ("Internal conflicts") is now real, the fourth of the 7 steps to get actual logic - the first genuinely new check in this redesign, not just a relocated existing one:** two different teachers in the same batch ending up scheduled in the same classroom at the same time now surface here as a resolvable pair instead of failing unworded (or, for the exact-match co-teaching shape, being silently merged with no confirmation at all). Each pair is classified and defaults accordingly: **co-teaching** (same subject and group - kept as-is, the existing merge logic already handles it correctly, this screen only adds visibility/confirmation) defaults to keeping both; a **split ("desdoble") session** (same subject, different groups sharing a room) defaults to **reassigning rooms** (two classroom pickers, both pre-filled with the colliding room, so at least one must actually be changed to resolve it); a genuine **room conflict** (different subjects) only offers picking one side to keep. Checked the UI/validation shape with the developer first, per the plan's own "Complexity flag" for this exact step: a flat dropdown with all options always visible, validated server-side on Continue, rather than a fancier widget hiding invalid options per row.
- User docs (`docs/{en,ca,es}/admin/working-schedules.md`) updated again for the new "Resolve teachers" step, alongside "Resolve groups".
- **Screen 5 ("Existing schedule conflicts") is now real, the fifth of the 7 steps to get actual logic:** the same classification/resolution shape as screen 4, but against an already-active `ems.attendance_schedule` from a *different* import (or a genuine double-booking of the same teacher across two incremental imports) instead of another entry in this same batch - previously always raised unconditionally on any such collision (no matter how legitimate), now shown and classified the same way: co-teaching (kept as-is), a split ("desdoble") session against an existing room (defaults to reassigning rooms), or a genuine conflict (defaults to keeping the new import's own data, archiving the conflicting existing session). No developer check-in needed before building it - the plan already fully specified this screen, including the trickiest part: reassigning an *existing* session's room has to go through the already-existing `ems.attendance_mixin._write_or_new_version()` helper (archive + clone with the new room) instead of a raw field write whenever that session already has real attendance history, a distinction resolved during an earlier same-day session's model-level work, well before this screen's own implementation began.
- Found and fixed while testing this screen: "left prevails" (the new import's data wins) only archived the *specific colliding schedule line*, not its parent template - if that was the template's only active line, it was left behind as an orphaned, empty record. Now the now-lineless template is archived too, matching the plan's own "archives/trims the existing session's template" wording.
- User docs (`docs/{en,ca,es}/admin/working-schedules.md`) updated again for the new "Existing schedule conflicts" step.
- **"Resolve teachers" (screen 3) gains a "Create new teacher" checkbox, superseding the "creating a brand-new one is deliberately not allowed here" note above (developer feedback after using the wizard for real):** some unresolved e-mails turn out to belong to a genuinely never-hired teacher, not a typo/mismatch of an existing one - forcing a pick from the (create-disabled) dropdown made no sense for those. Ticking **Create new teacher** locks the dropdown and creates a brand-new pending-identification teacher for that e-mail at Import, exactly like a placeholder code (`X1`, `X2`...) - except the file's own e-mail is kept and pre-filled as an editable **Work email** (**Assign corporate email manually** ticked), rather than left for a later "Generate Google account" to auto-generate, since the developer's own framing was "the e-mail can't be trusted as confirmed, but it's worth trying". Extracted `_get_or_create_pending_teacher(identifier, manual_email=False)` out of `_apply_import`'s previously-inline placeholder-code branch so both paths (a placeholder code, and now a create-new-ticked e-mail) share the exact same get-or-create-by-`schedule_import_code` mechanism, dedup-safe on re-import either way.
- User docs (`docs/{en,ca,es}/admin/working-schedules.md`) updated again for the new "Create new teacher" checkbox.

## Reason-aware "Archived" ribbon for students and teachers, plus a new student Expulsion outcome:
- Archived students now show **why** at a glance instead of a generic "Archived": a green **Alumni** ribbon (graduated), an orange **Withdrawal** ribbon, or a red **Expelled** ribbon — on both the form and the kanban card.
- Archived teachers show their actual departure reason the same way (**Retired**, **Resigned**, a new **Transfer** reason for teachers reassigned to a different centre, or **Fired**), also on both form and kanban — teachers' kanban previously showed nothing at all for an archived employee.
- A single reusable field widget (`ems_archived_reason_ribbon`) drives all of this for both models, reading a plain label + hex color pair (`archived_reason_label`/`archived_reason_color`) computed per model — see `docs/en/developers/contacts/contact.md` and `docs/en/developers/employees/employee.md`.
- `hr.departure.reason` gains a `color` field (same hex color-picker widget already used for `ems.attendance_status`/`ems.role`), so an admin can pick the ribbon color for each departure reason, including any new ones added later.
- New: the withdrawal wizard now asks the admin to choose between **Withdrawal** and **Expulsion** when archiving a student (voluntary vs. administrative withdrawal stays a free-text note, not a separate option). The confirm button's label adapts to the choice ("Withdraw"/"Expel"). Expulsion always results in `contact_type = 'expelled'`, even for a student who had already graduated once.
- A full audit of every place `contact_type`/`exit_type` was filtered or branched on (menu domains, search filters, `transition_status`, Google Workspace account suspension, `_academic_result()`, category sync) was done before adding the new `expelled`/`expulsion` values, to make sure none of them silently missed the new case.

## Pending-identification teachers from schedule imports:
- Importing a working-schedule file (per-teacher or the general cog-menu importer) no longer fails when a row names a not-yet-hired post with a placeholder code (e.g. `X1`, `X2`) instead of a real e-mail.
- A "Pending teacher (X1)" employee is created automatically, with the schedule/subjects/attendance lists already assigned — no manual setup needed.
- Re-importing an updated file for the same still-unstaffed post (same code) updates that same employee in place, never creating a duplicate.
- These employees show a "Pending identification" indicator (Teachers list column, kanban + form ribbon in a soft, non-garish yellow), with a matching search filter/group-by. The kanban indicator started as a badge under the name; changed to a ribbon (2026-08-01) to match the other reason-aware ribbons added to that same kanban right after it.
- Resolving a pending teacher's real identity reuses the existing "Generate Google account" button: fill in the real name + personal email, click the button — no separate confirmation step.

# Changes:

## Attendance templates now support several studies at once, lock their identity fields once real attendance exists, and get a "New version" action (`plans/attendance_template_multi_study.md`):
- `ems.attendance_template.level_id` removed entirely - never used in any report, and always derivable from `group_ids`/`study_ids`. `study_id` (`Many2one`) is now `study_ids` (`Many2many`): a template built for co-teaching/"desdoble" can genuinely span groups from more than one study, and `_write_schedule_sync` now unions every involved group's own study instead of keeping only the first one's.
- New `_check_subject_valid_for_all_studies` constraint: `subject_id` must actually be taught in **every** one of the template's `study_ids` (an intersection, backed by the new computed `allowed_subject_ids`), not just one of them.
- Once a template has real attendance history (new computed `has_sessions`, both on `ems.attendance_template` and `ems.attendance_schedule`), its identity fields become readonly: `teacher_ids`/`subject_id`/`study_ids`/`group_ids` at the template level, and each schedule line's own `weekday`/`space_id`/`start_time`/`end_time` at the line level. Editing them in place after real roll-calls exist would retroactively misrepresent what those sessions were actually about.
- Correcting a locked template (or a single schedule line) is now done via a new **"Edit"** button instead (icon `fa-pencil-square-o`; internally `action_new_version()` - labeled "New version" until 2026-08-05, renamed since from the user's side it reads as editing a locked record, not something that needs to advertise the archive+clone happening underneath - the confirm dialog still spells that out): it archives the template/line (cascading to its schedule lines for the template-level action) and opens a fresh, fully editable clone with no session history - already-taken attendance stays linked to the archived original. Archiving happens before cloning (not after), since cloning first would momentarily collide with the still-active original under the existing same-teacher/same-room `check_overlap` constraint.
- Also added icons to the template form's header buttons ("Reload students": `fa-refresh`) and fixed the schedule line's row button visually overlapping with the list row's own delete ("x") button - switched to `class="oe_stat_button"` (icon-only + tooltip), the same pattern already used for row buttons elsewhere in this codebase (`content_ids`/`outcome_ids`/`criteria_ids`).
- `ems.attendance_session_header`'s `group_ids`/`subject_id`/`space_id`/`template_teacher_ids`/`study_ids` (new) converted from `sudo()`-laden compute methods to genuine `related=` fields; `level_id` is no longer related to the template (which has none) and is instead computed from `group_ids[:1].level_id`. `ems.attendance_session_line.study_id` is likewise now `study_ids`.
- The template form is reorganized into a 3x3 grid (color/teachers; studies/start date/end date; groups/space/subject) and gains chatter (`mail.thread`/`mail.activity.mixin`).
- Migration `migrations/18.0.0.22.0/{pre,post}-migrate.py`: renames the old `study_id` column out of the way before schema sync, then backfills `study_ids` on the template and cascades it down to every existing session header/line via SQL joins.
- Documented in `docs/en/developers/attendance/{attendance_template,attendance_schedule,attendance_session}.md`; cross-references in `docs/en/developers/curriculum/{study,level}.md` and `docs/en/developers/employees/working_schedule.md` updated to match.
- The archive-or-write decision behind the "Edit" button is now a shared method, `ems.attendance_mixin._write_or_new_version(vals)` (`models/shared/attendance_mixin.py`), reused by the schedule-sync pipeline instead of each reimplementing the same `has_sessions` check. `_archive_stale_schedule_sync`/`_write_schedule_sync` (shared by the live Schedule tab's own edits and the working-schedule import wizard) changed from unconditionally archiving and recreating **every** schedule line of a persisting template to a per-line match: an untouched line is left alone, a changed line with no real sessions is updated in place (same DB id), and a changed line that already has sessions is archived and replaced with a fresh one - the same rule a manual edit already follows, now applied uniformly regardless of which caller triggers the sync.

# Fixes:

## Course transition wizard left archived templates' schedule lines active forever:
- Found while investigating what happens to teacher-side scheduling data across a course transition, in preparation for testing "Existing schedule conflicts". `course_transition_wizard.py`'s `_apply_cleanup` archived `ems.attendance_template` via a bare `write({'active': False})`, which bypasses `EmsAttendanceTemplate.action_archive()`'s own cascade to `attendance_schedule_ids`. A transitioned template went inactive, but its weekly schedule lines stayed `active=True` forever - invisible in the template's own (archived) form, but still matched by `classify_external_conflicts`/`find_self_conflicts`, silently contradicting those methods' own docstring assumption that a transitioned study has nothing active left to reconcile against.
- Fixed by switching to `action_archive()`. New regression test (`test_apply_archives_the_schedule_lines_of_an_archived_template`) creates a template with a real schedule line - the two pre-existing template-archiving tests never caught this because their own fixture creates templates with zero schedule lines.
- First of an 8-phase plan (`plans/course_transition_teacher_schedule_archival.md`) covering how the wizard should also archive affected teachers' `resource.calendar`/`resource.calendar.attendance` and roll them onto a new per-course calendar - the remaining phases are tracked separately, implemented one at a time.

## `test_data_main_cat_prefix` was red on a full, unscoped `./test.sh` run:
- `data/main/hr.departure.reason.csv` (added earlier for the reason-aware ribbon work below) deliberately overrides two native `hr.departure.reason` records to add a `color`, keeping their native `hr.` id prefix - a legitimate, documented exception (CLAUDE.md's "Data folder conventions"), but the test's own allowlist of accepted native-override ids was never updated to include them, so it flagged them as a naming violation. Fixed by adding `hr.departure_retired`/`hr.departure_resigned` to `ALLOWED_NATIVE_OVERRIDE_IDS` in `tests/test_data_main_cat_prefix.py`, matching the existing `hr.job_*` entries. Found running the full suite as the final gate for the `attendance_template` multi-study work, unrelated to that change itself.

## Every reason-aware ribbon showed the default red, never the actual color:
- `archived_reason_color` (Alumni's green, Withdrawal's orange, a departure reason's own color...) was only ever referenced through the `ems_archived_reason_ribbon` widget's own `color_field` option, never as its own declared `<field/>` in the view - and, unlike Many2many field widgets, this field registry's `relatedFields` mechanism turns out to only auto-fetch for x2many/many2one_reference field types in this Odoo version (confirmed by reading `web/static/src/views/fields/field.js`), never for a plain `Char` like this one. The color value was therefore never actually reaching the client, and the widget's own default-red fallback showed every time, regardless of the real color.
- Fixed by explicitly declaring `<field name="archived_reason_color" invisible="1"/>` alongside the ribbon field in all four views (`contact/{form,kanban}.xml`, `employee/{form,kanban}.xml`). New tour steps assert the actual rendered color (not just the text) to catch this specific regression going forward.

## Working-schedule import wizard showed a generic error popup instead of the usual red banner:
- An unresolvable group name or subject code in an uploaded schedule file raised uncaught from inside the onchange preview, so Odoo displayed it as a blocking modal dialog instead of the same in-form banner (with the Import button disabled) used for every other validation problem in this wizard (unknown teacher e-mail, missing classroom...).
- Both onchange handlers (`_onchange_file`, `_onchange_attachment_ids`) now catch that error and fold it into the same in-form banner, consistently with the rest of the wizard.
- That banner (and every other blocking, per-item problem: unknown e-mail, unresolved group/subject, missing classroom) now renders as an intro sentence + a real bullet list (one line per problem), matching the existing "these teachers already have a schedule" warning style, instead of one long comma-separated sentence.

## Import button could be clicked before file validation had actually finished:
- Attaching a file made the button visible/enabled immediately (it was only hidden once a problem was confirmed), so clicking fast enough could trigger the import before the background validation RPC returned.
- The button now starts hidden and is only ever shown once the same onchange positively confirms the file has no blocking problems - there is no window where it can render as clickable before that.

## Pending-identification info banner truncated a not-yet-hired teacher's full name to its first word:
- Both the blue "pending identification" banner and the actual pending-employee creation identified a not-yet-known teacher by naively taking the first whitespace-separated token of the planner row's raw `name` attribute, assuming the shape was always `"<code-or-email> <discardable label>"`. That assumption holds for a short placeholder code (`"X1"`) but not when the planner instead puts the person's own real, multi-word name in that field (e.g. `"Fulanito Menganito"`) - the old code silently kept only `"Fulanito"`.
- Fixed with a proper check (`_teacher_identifier`, `models/employees/working_schedule.py`): search the whole value for an actual e-mail pattern; if none is found, keep the entire (stripped) value as the identifier instead of just its first token. Applied uniformly everywhere a teacher node's `name` is parsed (`_onchange_file`, `_onchange_attachment_ids`, `create()`).
- The blue banner (`info_message` → `info_html`) now renders as a real bullet list too, matching the other banners in this wizard, instead of one comma-separated sentence.
- All four of this wizard's list banners (blocking issues, pending-identification, overridden teachers, external conflicts) now lay out their bullet list in up to 3 CSS columns (`ems_wizard_bullet_list` in `ems.css`) instead of one long single-column list, since these are short flat items and a long list was wasting the dialog's horizontal space - collapses to 1 column on narrow screens.
- Fixed a follow-up regression from the 3-column layout above (reported 2026-08-01): a single long line (e.g. one unknown-e-mail error, or one conflict line) had its own wrapped text visually split across all 3 columns instead of staying together in the first one - CSS multi-column's default fragmentation behaviour. Fixed with `break-inside: avoid` on each list item; verified in a real browser via a new tour assertion (bounding-box width check) rather than trusting the CSS fix by reasoning alone.

## A not-yet-identified teacher's unresolved group/subject showed a generic error popup on Import click, not the red banner:
- The onchange preview never actually parsed a pending-code teacher's schedule content (subject/group resolution) - it only noted the code as "pending" and moved on. An unresolvable group acronym (or subject code) in that same row therefore passed the preview silently and only surfaced later, as an uncaught `ValidationError`, when actually clicking Import (`create()`) - Odoo's generic error dialog instead of the wizard's own red "blocking issues" banner.
- Fixed: `_onchange_attachment_ids` now parses every teacher node's schedule content up front regardless of whether its code/e-mail resolves to a real employee yet, so an unresolved group/subject is caught and listed as a blocking issue immediately, hiding the Import button - matching the exact same treatment a known teacher's unresolved group/subject already got.

## Working-schedule import wizard looked hung while a file was being processed:
- Attaching a file to either upload field (the per-employee scoped `file` or the general cog-menu's `attachment_ids`) triggers a server-side onchange that parses the whole planner XML - slow enough, with zero visual feedback, to look hung.

## "Pending identification" kanban badge showed on every teacher, not only pending ones:
- The badge's `t-if` read `record.pending_identification.value` - for a kanban record, `.value` is the *formatted* display value (for a Boolean field, Odoo's formatter returns an HTML checkbox markup string, which is always truthy regardless of true/false); `.raw_value` is the actual boolean and is what a conditional must use. Confirmed by reading Odoo's own `getFormattedRecord`/`formatBoolean` and by reproducing the bug live via a browser tour (a non-pending "confirmed" teacher's card also showed the badge).

The pre-existing `tutorships` badge's `t-if` had the same `.value`/`.raw_value` mix-up (harmless in practice only because Char's formatter happens to return the same string) - fixed for consistency while in the area.

## `devel.sh` left `hr.employee.work_email` stale after replacing real e-mails:

## Archiving a group with active students now asks for a single, clear confirmation:

Archiving one that still has active `main_student_ids`/`reinforcement_student_ids` now shows a clear 4-paragraph confirmation explaining exactly that (no student is removed, the group just stops showing in default views, and the end-of-course transition will still clear it if that's the reason), with **Proceed**/**Cancel** actions, instead of archiving silently.

- `views/community/group/{form,list}.xml` now declare the `active` field (invisible) - discovered empirically that Odoo's Archive/Unarchive Action-menu item only appears on a view that declares this field itself, not just on the model.
- The group's form now shows the standard Odoo "Archived" ribbon when inactive (same `web_ribbon`/`invisible="active"` pattern used natively across Odoo core), so an archived group is visible at a glance, not just via the Action menu's label.

## Groups can now be archived and reactivated instead of duplicated:
- `ems.group` gains the standard Odoo `active` field (default `True`) — a group not running this course but that may come back in a future one (a cycle skipping a year, a shift suspended temporarily...) can now be archived via the Action menu (Archive/Unarchive), keeping its history (tutor, classroom, past students/schedule) instead of losing it to a delete-and-recreate cycle.

## `resource.calendar.attendance` gains an `active` field (phase 2 of the course-transition archival plan):
- Core Odoo's model has none. Added so a later phase can archive a teacher's migrating calendar blocks at course transition instead of `unlink()`-ing them, which would destroy the exact history a "who taught what, which course" query needs (`plans/course_transition_teacher_schedule_archival.md`). All 1436 existing rows auto-backfilled to `active=True` by Odoo's own new-column handling. Nothing writes `active=False` here yet - that's a later phase.

- **Explicitly confirmed, and pinned down with regression tests, that archiving an `ems.attendance_schedule` line must never cascade to its `ems.attendance_session_header` records, in either direction**: once a line `has_sessions`, its logistics fields are readonly, so a routine correction (e.g. fixing its room) silently archives the old line and clones a new version (`action_new_version()`) as a side effect of what looks like a normal in-place edit - if that cascaded to sessions, every such correction would wipe the line's attendance history from a teacher's default view, the opposite of the intent. New tests: `test_action_archive_does_not_cascade_to_sessions`, `test_action_archive_on_template_does_not_cascade_to_sessions` (`tests/test_attendance_template.py`).

- `get_employee()` now prefers the stored `employee_id`, falling back to the pre-existing reverse search (`hr.employee.search on resource_calendar_id`) for a calendar predating this field - keeps working once a calendar is no longer any employee's *current* one.
- Both fields are blank on every calendar created before this phase; not yet backfilled by a migration (pending a decision on bumping the manifest version for it). Also deliberately not yet touched: the XML batch importer's own calendar-minting-by-name-search logic (`_write_teacher_schedule`) - still creates calendars the old way for now, a later phase ("the wizard takes over calendar creation") replaces it.

## New shared lookup: `ems.attendance_mixin.find_schedule_lines_for_slot` (phase 4 of the course-transition archival plan):
- `resource.calendar.attendance` (a teacher's weekly calendar block) and `ems.attendance_schedule` (the recurring class-session line) have no direct FK - only an inferred `(weekday, hour_from/start_time, hour_to/end_time)` match. ## Course transition now actually archives teacher calendar blocks and their schedule lines (phase 5c of the course-transition archival plan):
- New `ems.course_transition_wizard._apply_calendar_archival()` (step 7a, right after the existing template-archival step): archives every migrating calendar block found by phase 5b's query, then finds the matching `ems.attendance_schedule` line(s) via the phase-4 lookup and either archives the line + its sessions (when the underlying template already got archived by the existing, unconditional per-study mechanism - the common case, where this call just catches up the sessions that mechanism's own cascade deliberately skips) or, for a line the template-side never touched (a calendar drifted to reference an in-scope group its own template doesn't), checks whether another teacher's calendar still has an active block for that exact slot before deciding to keep the line alive (dropping only the departing teacher from `teacher_ids`) or archive it outright.
- Found and fixed a genuine ordering bug while testing this against real fixtures: the initial version searched only *active* schedule lines, so a line already archived moments earlier by the template-cascade was silently skipped - meaning its sessions never got explicitly archived at all, the exact gap this phase exists to close. Fixed by searching with `active_test=False` and branching on the line's own current `active` state.
- New tests in `tests/test_course_transition.py`: `test_apply_archives_the_migrating_calendar_block`, `test_apply_leaves_an_out_of_scope_calendar_block_active`, `test_apply_archives_the_matching_schedule_line_and_its_sessions`, `test_apply_archives_the_template_once_its_only_line_is_archived`, `test_apply_removes_only_the_departing_teacher_when_another_still_has_an_active_block`, `test_apply_creates_a_new_template_version_when_the_departing_teacher_has_sessions`, `test_apply_with_no_migrating_calendar_blocks_is_a_no_op`. `TestCourseTransition` (104 tests) green.
- **Corrected same day (developer caught it in review): removing a departing co-teacher must never write `teacher_ids` directly.** The first version dropped the departing teacher via a raw `line.attendance_template_id.teacher_ids -= departing` write - `teacher_ids` is a locked identity field once the template `has_sessions` (see `attendance_template.md`'s "Identity fields, locking, and the 'Edit' button"), so this would have retroactively rewritten every already-taken session's own `template_teacher_ids` (a `related` field), corrupting who *actually* co-taught each past session. Fixed by deciding **once per template** (not once per line/teacher) with the *full* set of departing teachers found across all of that template's migrating lines, then going through `_write_or_new_version()` (`ems.attendance_mixin`) - the exact same mechanism the "Edit" button already uses: writes in place only if there's no session history yet, or archives the original (leaving its `teacher_ids`/sessions historically untouched) and clones a corrected version otherwise. Deciding per template also means a template every one of whose co-teachers departs in the same run is simply archived outright, no needless clone ever created.

## Found and fixed two real, pre-existing bugs in `ems.attendance_mixin`/`action_new_version()` (shared by the "Edit" button and now phase 5c above):
- **`ems.attendance_template.attendance_schedule_ids` was missing an explicit `copy=True`.** Odoo's `One2many` field defaults to `copy=False` - without the override, `action_new_version()`'s clone silently ended up with **zero schedule lines**, for any template with real session history, since it was first built. Undetected because the only existing test never asserted the clone's lines were actually there.
- **The clone's follow-up `.action_unarchive()` needed `with_context(active_test=False)`.** Even with `copy=True` fixed, the freshly-copied (still-inactive) lines are excluded by a plain O2M read's default active filtering, so the unarchive call was silently a no-op on an empty recordset.
- Also disabled the generic Odoo "Duplicate" action on `ems.attendance_template`'s views (`duplicate="0"`) - now that lines genuinely copy, a plain Duplicate (which never archives the original first, unlike `action_new_version()`) would immediately self-collide via `check_overlap`.
- New regression assertions added to the existing `test_action_new_version_template_archives_and_clones_whole_template` (`tests/test_attendance_template.py`): the clone's `attendance_schedule_ids` now must actually exist, be active, and match the original line's weekday. `TestAttendanceTemplate` (25 tests) green.
