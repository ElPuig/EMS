# Breaking changes:

## Attendance templates can no longer be created or archived by hand, admin included:
- Second half of `plans/calendar_driven_attendance_templates.md`'s point 3 (locking template creation/archival to be calendar-driven only). `security/ir.model.access.csv` revokes `create`/`unlink` on `ems.attendance_template` for every group (previously full CRUD for admin and teacher). The "New" button is hidden entirely on the list/form views (`create="0"`); the generic "Archive" action is additionally hard-blocked with an explanatory error by a new `write()` override, since Odoo has no clean way to hide just that one menu item without also blocking legitimate direct edits (color, etc.).
- Confirmed safe before making this change: `ems.course_transition_wizard._templates_to_archive()` already archives a template purely by its own study-scoped `group_ids`, independent of how it was created - a manually-created template would still be correctly archived at course transition, no orphan risk either way.
- Going forward, a template only ever comes into existence (or goes away) as a consequence of `sync_from_schedule_batch()` reconciling a teacher's calendar, or a course transition. Every legitimate internal call site (the sync pipeline, `course_transition_wizard`, the import wizard's own room-reassignment conflict resolution) now runs with an internal bypass context flag plus `sudo()`, so this doesn't block the pipeline itself regardless of which user (even an admin) triggered the schedule edit/import.

## On upgrade, every attendance template is archived and rebuilt from each teacher's current working schedule - a teacher without one cannot take attendance:
- This version's own migration (`migrations/18.0.0.22.0/post-migrate.py`) now calls the new `ems.attendance_template.regenerate_all_from_calendars()`: every active template is archived outright and a fresh, calendar-backed set is rebuilt from each teacher's CURRENT `resource.calendar.attendance` rows, before the upgraded service is reachable by any user (so this is never visible as an intermediate broken state).
- Real, explicit consequence (developer's own call): a teacher whose personal working schedule was never (re)loaded onto their calendar ends up with zero active templates after this upgrade, and cannot take attendance until a real schedule is imported/entered for them - there is no way to route around this, since points 1-4 of `plans/calendar_driven_attendance_templates.md` make a template exist only as a consequence of a real calendar.
- A second, narrower case of the same breaking change: when two teachers' current calendars genuinely clash (same room/weekday/time, different subject, not recognized as co-teaching - see `regenerate_all_from_calendars()` below), one side is dropped rather than aborting the whole upgrade. Confirmed against a real production snapshot: this centre has support/reinforcement teachers recorded under their own subject, physically sharing a room/slot with the group's main teacher - exactly this shape. Every dropped entry is logged by name (teacher, subject, slot, and what it conflicted with) so it can be reviewed and fixed by hand afterward via the Schedule tab - nothing is guessed automatically.

## Attendance template identity fields and schedule lines can no longer be edited by hand either, admin included:
- Second refinement of point 3, same day: the developer found `teacher_ids`/`subject_id`/`group_ids`/`study_ids`/`start_date`/`end_date` were still freely writable on the template (only `active` was locked before), and `ems.attendance_schedule` had no lock at all - lines could be added/removed/edited directly through the template's own embedded list. Both are now locked the same way: `ems.attendance_template`'s `write()` guard extended to cover all of those fields (only `color` stays free); `ems.attendance_schedule` gained its own `write()` guard covering everything except `student_ids`, plus `create`/`unlink` revoked in `security/ir.model.access.csv` (matching the template's own `1,1,0,0`).
- `ems.attendance_template.space_id` removed from the model entirely (not just locked) - developer's own call, since it only ever existed as a default-value source for manually adding a schedule line, itself no longer possible either. `ems.attendance_schedule.space_id` (the line's own room) is unaffected.
- `ems.attendance_mixin._write_or_new_version`'s in-place-write branch didn't carry the internal lock-bypass context at all before this fix (only its archive+copy branch did) - every legitimate internal caller on either model (the sync pipeline, `course_transition_wizard`'s departing-co-teacher correction, the import wizard's room-reassignment resolution) now correctly bypasses both branches.
- Views updated to match: the template form's identity fields are unconditionally readonly (not just once `has_sessions`); the embedded schedule-line list lost its `space_id` column and gained `create="0" delete="0"`, with its remaining columns unconditionally readonly too.

## The manual "Edit" button on a locked template/schedule line (`action_new_version`) was removed:
- Developer's own call, now that a template's identity can only change as a consequence of editing the calendar: *"Este mecanismo que hicimos para 'editar' templates o schedules ha quedado obsoleto."* The underlying shared mechanism (`ems.attendance_mixin._write_or_new_version()`) was NOT removed - it's still used internally by the schedule-sync pipeline, `course_transition_wizard`'s departing-co-teacher correction, and the import wizard's room-reassignment resolution. Only the direct, button-driven entry point is gone.

# What's new:

## The same weekday/time/room slot can now hold two different subjects across the year, each with its own date range:
- Real scenario: a module runs until February, then the end-of-course project takes over the exact same slot for the rest of the year - both entered on the calendar upfront (in September), instead of requiring someone to remember to edit the calendar on the actual handoff day.
- Reuses core Odoo's own `date_from`/`date_to` fields on `resource.calendar.attendance` (not new EMS fields) - a first draft that added parallel EMS-only fields collided with core's own "Attendances can't overlap" constraint, which specifically exempts a row that already has these fields set. `ems.attendance_schedule.check_overlap()` already filtered candidates by template date-range overlap, so once the dates flow from the calendar block into the derived template (`ems.attendance_template._plan_schedule_sync`), no genuine conflict is raised for two non-overlapping-dated blocks sharing a slot.
- Schedule tab edit mode redesigned around independent per-day cards (5 weekday columns, each with its own "+ Add" and per-card remove button) instead of a shared row across all 5 days - each card carries its own start/end time, its own optional date range (blank = whole course year, unchanged default), subject-or-non-teaching reason, group, and room (newly exposed as an editable per-card field, previously only ever inferred server-side). Two cards on the same weekday can share the exact same time to implement the mid-course handoff - no dedicated "split" action, just add a second card and match its time to the first. No drag-and-drop between cards/days. Read-only view mode is unchanged: two entries sharing a slot still render side by side instead of one hiding the other. Interactive tour: `ems_working_schedule_split_period`.
- `get_schedule_hours_summary()` (the Schedule tab's own weekly-hours totals, also reused by the PDF report) now counts a date-split slot only once (the longer entry), not once per date-scoped row - `_dedupe_date_split_blocks()` clusters same-weekday entries by time overlap before summing.
- `regenerate_all_from_calendars()`'s own conflict-dropper (`_drop_unresolved_conflicts`) is also date-aware now - two entries whose date ranges genuinely don't overlap were never a real conflict and must not be dropped.

## Student roster moved from the template to each individual weekly schedule line:
- Point 1 of `plans/calendar_driven_attendance_templates.md`. `ems.attendance_template.student_ids` moves to `ems.attendance_schedule.student_ids` - a specific day/time slot can now genuinely have a different attendee list (someone absent that day, an extra student sitting in) without needing a whole separate template just for that. `fill_students()`/`reload_students()` move with it; the template form's old "Students" tab is gone, replaced by a "Students" button per schedule line opening that line's own form (a full class roster doesn't fit an inline list row).
- Every real write path updated: session-line population (`ems.attendance_session_header._auto_populate_lines`, now one hop shorter since sessions already FK directly to the schedule line), the enrollment add/remove sync hooks (`ems.enrollment`), and the student-withdrawal operational-records cleanup (`res.partner._ems_clear_operational_records`).
- Existing data: the now-orphaned old relation table is dropped in `migrations/18.0.0.22.0/post-migrate.py::_drop_old_attendance_template_student_rel` (confirmed empirically that Odoo's own schema sync does NOT do this automatically for a removed Many2many, unlike a plain column) - no data is carried forward from it. An earlier version of this migration copied each template's roster onto its current schedule lines first (a pre-migrate backup + post-migrate restore roundtrip); removed (2026-08-12) after tracing the actual code showed the copied data was always immediately discarded anyway - `regenerate_all_from_calendars()` (called right after, same migration) archives every template the restored rows would have landed on and rebuilds a fresh set via `fill_students()` (current `ems.enrollment`), which never reads the restored roster. Found while re-testing this migration against a real, already-migrated production snapshot.

## The working-schedule import wizard's final "Overall summary" screen now auto-downloads a CSV of the run:
- Developer feedback: a colleague's `course_transition_wizard` already auto-downloads a CSV the moment its own last screen renders ("cuando lleguemos al final del asistente (overall), se descarga un fichero con ese resumen") - this wizard's own last screen now does the same, same mechanism (the pre-existing `auto_download_binary` widget, already used by 4 other wizards).
- New `summary_file`/`summary_file_name` fields, populated by `_continue_from_db_conflicts()` from the exact same data already feeding the on-screen "Overall summary" cards (a single `sections` list built once, fed to both renderers, so the file and the screen can never disagree) - two columns (`Category`, `Detail`), one row per detail line.

## A group missing a classroom can now be fixed directly from the working-schedule import wizard's "Resolve groups" screen:
- Developer feedback, after hitting the error on a real import ("These groups have no classroom assigned, so their schedule cannot be imported: SA2A"): "Quiero que podamos arreglarlo desde 'Resolve groups'" - a group already matched by name in the file but still missing `ems.group.space_id` used to only surface at the very last "Import" click. Now caught right after the intro screen, alongside the existing unresolved-group-name list, as its own new `space_line_ids` list on the same "groups" step.
- The classroom picked here is written straight onto the real `ems.group.space_id`, not wizard-scoped - fixed for this import and every future one. A group that only becomes known-missing-space AFTER this step (e.g. a brand-new group created on the spot while resolving an unmatched raw name) is still caught by the pre-existing final safety net at Import, just not pre-emptively on this screen. Interactive tour: `ems_working_schedules_import_resolve_missing_classroom`.

## New uniqueness guard against duplicate teaching assignments:
- Point 2 of the same plan. No two ACTIVE templates may share the exact same `(subject_id, teacher_ids-as-set, group_ids-as-set)` triple. Deliberately EXACT-match, not "any group overlap": a real, legitimate pattern exists in this centre's own data where the same teacher teaches the same subject to a group alone AND to that group combined with another, in genuinely different templates (a "desdoble" - combined one day, split another) - confirmed with the developer this is not a duplicate to reject.

# Fixes:

## Teachers created before 2026-07-12 could end up with no personal working-schedule calendar at all:
- `hr.employee.create()`'s auto-calendar creation only started with commit `bc29e04b` (18.0.0.20.0) - any teacher already in the database before that (or whose `employee_type` only became `'teacher'` later) could have `resource_calendar_id` empty. The working-schedule importer silently no-ops writing onto an empty calendar, leaving a teacher with real `ems.teaching` rows but an empty "Schedule" tab, with no error shown anywhere.
- Backfilled for both paths: a fresh install (`post_init_hook`) and an existing installation upgrading (`migrations/18.0.0.22.0/post-migrate.py`) now create a real personal calendar for every teacher still missing one, mirroring `create()`'s own logic exactly (shared via a new `hr.employee._ems_create_personal_calendar()` helper). Verified against this dev database: 7 real teachers backfilled.

## `TestAttendanceArchivedFilterTour` was left broken by point 3's archival lock:
- Found by the full, unscoped `./test.sh` gate: `tests/test_attendance_archived_filter_tour.py`'s own fixture setup called `template.action_archive()` directly (needing an already-archived template for the tour to filter on) - a leftover from before the write() guard existed, missed when every other similar fixture across the test suite was updated during point 3's own rollout. Fixed with the same `.with_context(ems_bypass_template_lock=True)` bypass already used everywhere else for legitimate test setup.

## Derived breaks (patio) could go missing on a teacher's calendar view for a day their real entries didn't happen to span into the break's own hour:
- Found by the developer testing two real teachers after the Schedule tab card redesign: one whose calendar alternates morning-only some weekdays / afternoon-only others never saw a break on the "wrong" weekdays; another who works afternoon-only every day was shown a morning break that never applied to him while his own real afternoon break didn't show at all.
- `hr.employee._get_derived_break_entries()` computed containment against each individual day's own known span - correct for a uniform daily pattern, wrong for one that varies morning/afternoon by weekday. Redesigned to compute a whole-week morning/afternoon span instead: a break candidate now shows on every weekday the teacher works that half of the day at all (even a day they're off entirely), and never shows for a half they never work at all during the week - still skipped on any specific day it would overlap that day's own real entry.
- Classification recomputes morning/afternoon from each entry's own `hour_from` (matching the Schedule tab widget's own threshold) rather than trusting the stored `day_period` field, which two different write paths populate with two different, disagreeing thresholds of their own.
- Verified empirically against both real teachers' actual calendars, not just backend tests.

## Schedule tab kept showing the PREVIOUSLY viewed teacher's own hours summary/derived breaks after paging to a different one:
- `schedule_grid_field.js` only ever loaded `_loadSummary()`/`_loadDerivedBreaks()` from a mount-only hook (`onWillStart`) - Odoo's form view reuses the same widget component instance across a pager/breadcrumb navigation to a different employee (no remount), so the previous teacher's data stuck around until a full page reload.
- Fixed with `useRecordObserver` (reloads on every genuine record change, not just on mount) - with a real gotcha along the way: the hook's own `record` argument has to be used, not `this.props.record`, which can still be the previous employee at the exact moment the callback fires.
- New regression tour (`working_schedule_stale_breaks_tour`) pages between two fixture teachers and asserts the first's own break stops showing on the second's calendar.

## Derived breaks (patio) could show an unrelated program's break, not just the teacher's own:
- Candidate breaks were searched across every schedule framework unconditionally - a teacher genuinely teaching only a CCFF program (e.g. CFGS/EFPS) was shown that program's own break correctly, but also two unrelated ESO breaks that happened to fit by time alone.
- Now scoped to the level(s) the teacher actually teaches (`teaching_ids.group_id.level_id`, kept in sync with the real calendar) - falls back to searching every framework only when the teacher has no identifiable level at all. A teacher spanning several levels whose frameworks share the same break (ESO/Batxillerat) still sees it once; one genuinely spanning different configurations (ESO + CCFF) sees only their own relevant breaks.
- Verified empirically against the reporting teacher's real calendar and two others checked earlier in this same investigation.

## `TestCourseTransition.test_apply_leaves_a_future_justification_with_no_session_active` was flaky in the last hour of any day:
- `future.replace(hour=23, minute=0)` produced an `end_date` earlier than `start_date` whenever the real wall-clock time the test happened to run at was already past 23:00 with a nonzero minute (`start_date` kept that same minute, `end_date` didn't) - tripped `ems.attendance_justification`'s own "completion date must be later than start date" constraint. Found by chance running the full class at 23:16.
- Fixed by fixing the fixture's hour/minute/second explicitly (8:00/23:00) instead of inheriting the current wall-clock time - the test only needs the date itself to be years in the future, never depended on "now"'s own time of day.

## Two more test files left broken by the field-locking/`space_id` removal, only caught by the full, unscoped `./test.sh`:
- `test_attendance_session.py::test_space_id_comes_from_schedule_line_not_template` wrote `schedule.space_id` directly (now locked) and separately compared against `template.space_id` (removed entirely) - neither had been touched by the original locking/removal passes, since this file wasn't among those exercised by the scoped test batches used at the time. Fixed with the same `ems_bypass_template_lock` context used everywhere else for legitimate test setup, and re-pointed the "not equal to" comparison at a second schedule line's own room (the only meaningful differentiator left, now that room is exclusively a schedule-line concept).

# Internal changes:

## i18n and full user documentation pass for this branch's whole feature set:
- `i18n/{ca_ES,es_ES}.po`: added the 3 strings introduced by the Schedule tab card redesign (`Remove card`, `Valid from/until (blank = whole course year)`) that a full `--i18n-export` diff showed missing - verified functionally via `odoo.tools.translate.CodeTranslations`, not just a `.po`-file read, since these are JS/XML code strings with no DB-side representation to spot-check.
- `docs/{en,ca,es}/admin/working-schedules.md`: "Edit a Teacher's Schedule" rewritten for the card-based UI (replacing the earlier shared-row/"Split" description), new "Mid-Course Subject Handoff" section, and a short note on auto-filled breaks/side-by-side rendering added to "View a Teacher's Schedule". `docs/{en,ca,es}/teachers/working-schedules.md` got the equivalent read-only-perspective note. Two real screenshots captured against a disposable fixture teacher (never real student/teacher data) - a first attempt using common curriculum-sounding fixture subject names ("Programació") picked a real, unrelated seeded subject via `selectByLabel`'s substring matching instead of the fixture's own; renamed to names confirmed (via psql) to have zero substring overlap with any real seeded data.

## `resource.calendar.attendance` now carries a real FK to the `ems.attendance_schedule` line it represents:
- First phase of `plans/calendar_driven_attendance_templates.md` (point 4 only - the rest of that plan is still proposed, not implemented). Until now, the link between a teacher's weekly calendar block and the recurring class-session line it maps to was purely inferred by content matching (teacher + subject + group overlap + weekday/time) - fragile, and the exact class of bug fixed earlier this same branch (a stale room match silently breaking the link).
- New `resource.calendar.attendance.attendance_schedule_id` (Many2one) is captured automatically at the end of every schedule sync (`ems.attendance_template._link_calendar_attendance`, called from both `sync_from_schedule_batch` and `sync_from_schedule_batch_fresh_import`) - both the live "Schedule" tab edits and the XML batch importer. Correctly handles co-teaching (several teachers' own personal calendar rows all pointing at the same shared schedule line) and an untouched co-teacher whose slot survives a merge.
- Deliberately no historical backfill: rows written before this change keep the field empty rather than re-running the same ambiguity-prone inference this FK exists to stop needing. `find_schedule_lines_for_teaching` (the old inference lookup) is unchanged and still the fallback for any pre-existing block - `course_transition_wizard` has not been switched over yet.

## `regenerate_all_from_calendars()` replaces a one-off duplicate-merge migration:
- Testing this version's migration against a real production snapshot found 2 real exact-duplicate `ems.attendance_template` pairs that the new uniqueness constraint would otherwise reject on upgrade. The first approach written was a dedicated migration step that detected and merged each pair line-by-line. Abandoned (developer's own call) once it became clear the whole class of stale/duplicate data is moot the instant every active template is archived and rebuilt from the current calendar anyway - `regenerate_all_from_calendars()` (`ems.attendance_template`) does that, and is what the migration now calls instead. See `plans/calendar_driven_attendance_templates.md`'s "Production migration sequencing: built for real, 2026-08-11" section for the full reasoning.
- Takes an optional `teachers` recordset to scope both the archive and the rebuild to a subset instead of every teacher in the database - added so it can be tested (and potentially reused for a future partial/admin-triggered regeneration) without touching or depending on every other teacher's real, unrelated schedule data.
- Also re-testing against the same production snapshot found a real, unresolved room-conflict pattern (support/reinforcement teachers under their own subject) that made the batch abort entirely. Rather than widening the general-purpose co-teaching detection (`is_co_teaching_with`, also used by `check_overlap` for every live schedule edit - too risky, would blunt its ability to catch a genuine double-booking mistake), `_drop_unresolved_conflicts` scans for exactly this shape before the sync runs and drops one side so the rest of the batch still regenerates cleanly - every drop is logged by name for manual follow-up. Confirmed with the developer this design goal is deliberate: this version should be deployable on any live EMS instance without first requiring a course transition to blank every calendar - and confirmed that the working-schedule import wizard's own conflict resolution (`_classify_conflict_kind`) has the exact same gap today (this cross-subject case is classified as `plain_conflict`, whose only resolutions are a fictional room reassignment or dropping one side entirely) - so this isn't a shortcut specific to the migration, it's the same real limitation surfacing either way.
