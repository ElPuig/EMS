# What's new:

## Guard duty schedule board:
- New "Guard duty schedule" screen under **Employee Attendances** (sibling of "Correction Requests"), open to every teacher (`ems.group_teacher`), not just Head of Studies/Direction — deliberately not placed under "Working Schedules" (too restrictive) since colleagues' schedules aren't secret, per developer feedback during planning.
- Read-only, centre-wide aggregation of every teacher's occupied time blocks: weekday tabs (Monday-Friday) plus a Morning/Afternoon shift dropdown within each day (they're separate shifts, shown one at a time, not stacked together), columns = groups taught in that shift, rows = time blocks, plus a "Guard duty" list per row for whoever's on guard duty then. No new data captured — reads the same `resource.calendar.attendance` rows teachers already fill in on their own personal schedule (Working Schedules' Schedule tab).
- New `is_guard` Boolean on `ems.non_teaching_type` (seeded `True` on the "Guard" row) marks which non-teaching reason(s) count toward this board — data-driven, same pattern as the pre-existing `is_break`/`is_fixed`.
- "Download PDF" button, next to the shift dropdown, exports the currently open day only (both shifts, one page each) — not the whole week — as a printable document, following the same pattern as the existing teacher/group schedule PDFs.
- No dedicated model: the board's methods extend `ems.course` directly (`models/attendance/guard_duty_board.py`), and the screen itself is a plain `ir.actions.client` (not bound to any record) — new field `resource.calendar.attendance.non_teaching_is_guard` (related, mirrors the existing `non_teaching_is_break`), new client-action component `guard_duty_board.js`/`.xml`/`.css`, new report `reports/attendance/report_guard_duty_board.xml`.
- No new ACL needed anywhere — `ems.course` already grants every teacher read access, and base Odoo's own `resource` module already grants every internal user plain read access to `resource.calendar`/`resource.calendar.attendance` too (confirmed empirically; the same fact already applies to the pre-existing group-schedule aggregation).
- Full trilingual docs: developer reference (`docs/en/developers/attendance/guard_duty_board.md`) and a teacher user manual in English/Catalan/Spanish (`guard-duty-schedule.md`), plus real ca/es i18n entries for every new string.
- Backend `TransactionCase` tests (including a dedicated regression test proving a plain teacher can read every colleague's schedule without an `AccessError`) and a full browser tour covering weekday-tab switching and the PDF export.
- Post-review fixes (developer testing, 2026-08-31): removed the meaningless "New" button and the raw `ems.guard_duty_board,<id>` window title (`create="0" delete="0"` on the form + a `_compute_display_name()` override showing "Guard duty schedule (<course>)"). More importantly, fixed every weekday except Monday rendering empty in the live screen even though the PDF always showed the full week correctly — the widget was reading its data from the field's own prefetched sub-records, which the web client silently caps for a centre-wide aggregation this size (several hundred rows); switched it to fetch one weekday/shift at a time via a new JSON-safe RPC method (`get_guard_duty_board_data`) instead.
- Second round of readability fixes (same day): afternoon shifts were too cluttered to read at a glance. Cells now show the subject's short code (e.g. "MP 0440") instead of its full title, and every co-teacher's name (previously only the first one, silently dropping the rest on a co-taught class) — same simplification applied to the PDF. The table now scrolls horizontally instead of squeezing every group into an unreadably thin column, and the Time block / Guard duty columns (the two with the densest content) get more room than a single group's own column.
- Third round (same day): the URL bar showed a raw `ems.guard_duty_board/<id>` instead of a proper `action-<xmlid>` like every other EMS screen, because the previous design's launcher was a dynamic server action with no static xmlid of its own to put in the URL. Fixed by moving the board's own methods onto `ems.course` (see above) and replacing the wizard-record/server-action combo with a plain `ir.actions.client` — a real, stable, URL-addressable action. Also fixed the group columns not all being the same width across tables (and the horizontal scrollbar existing but not actually reaching the last column) — switched from content-based auto-sizing to a fixed `table-layout` with an explicit `<colgroup>`, so every group column shares one identical, predictable width and the scroll container always has an exact width to scroll against; regression-tested in the browser tour (scrolls to the reported max and asserts the last column is then fully visible).
- Fourth round (same day): after the round-3 rewrite, neither scroll axis worked at all anymore (not just imperfectly) — the new page's root had no explicit height, so Odoo's own action container silently clipped any content taller/wider than the viewport with no scrollbar. Fixed the same way the existing attendance pass-list screen already does it: the root gets `height:100%`/flex-column, only the content area scrolls (vertically), with the table's own wrapper still scrolling horizontally inside that — both now regression-tested in the tour. Also split Morning/Afternoon into a proper dropdown instead of showing both stacked on the page (per developer feedback: separate turns, not one long page), and moved the "Download PDF" button inside each day's own toolbar, scoped to export just that one day (both shifts) instead of the whole week — the report template now reads which day was active from the print button's own context instead of always looping all 5.
- Fifth round (same day): the "one PDF per day" fix above still exported both shifts on that day; now it exports only whichever shift the dropdown had selected (same context-based scoping, a new `guard_duty_shift` key). Also gave the PDF the same fixed, uniform column widths as the live screen (`<colgroup>` + `table-layout: fixed`, scaled down for print) — while verifying this against a real generated PDF, found and fixed one more real bug the live screen didn't have: a single unbroken long value (an unlinked "Pending teacher (email@...)" placeholder, no spaces to wrap at) still forced its whole column wider than the rest even under a fixed layout, until word-breaking was explicitly allowed on the cell text.
