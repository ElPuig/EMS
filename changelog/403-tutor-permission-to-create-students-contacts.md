# Fixes:

## Wrong Catalan/Spanish label on the surname field:
- `res.partner.lastname` (from the external `partner_firstname` module) showed "Segon Cognom" in Catalan and "Apellido" in Spanish on the student/contact form, instead of "Cognoms"/"Apellidos" - a leftover from an unrelated module (`partner_second_lastname`, currently uninstalled) that had polluted this field's stored translation at some earlier point.
- Fixed via `i18n/ca_ES.po`/`i18n/es_ES.po`: added `partner_firstname.field_res_partner__lastname` and `field_res_users__lastname` as extra references on the existing "Last name" translation block, whose msgstr was also corrected to the plural form. This block is shared with two other EMS fields (`ems.contact.relation.wizard.lastname`, `ems.grade_outcome_line.student_lastname`) that hold the exact same kind of data (combined surnames), so they now consistently read "Cognoms"/"Apellidos" too.
- Verified directly against `ir_model_fields.field_description` in the DB after `./upgrade.sh` (a `.po` entry existing is not proof by itself - see the i18n verification rule in CLAUDE.md).

## First name field was locked for tutors while the visible surname field silently wasn't:
- On the student form, "Nom"/"Nombre" (firstname) was correctly read-only for a tutor editing their own student, but "Cognoms"/"Apellidos" (lastname) was unexpectedly editable regardless of role - the opposite of what was intended, and also the opposite of what the developer actually wants now (both should be editable by the tutor, so a data-entry typo can be corrected).
- Root cause: `partner_firstname.view_partner_form` renders the `lastname` field twice (order depends on the `partner_names_order` system parameter - only one copy is visible at a time), plus two more copies inside the `child_ids` inline sub-form. EMS's own view (`ems.view_contact_form_firstname`) targeted `lastname` via a plain `<xpath expr="//field[@name='lastname']">`, which Odoo's view inheritance resolves to only the *first* matching node in document order (confirmed by reading `odoo/tools/template_inheritance.py::locate_node`, and empirically via `get_view()` in `odoo shell` - the first occurrence happened to be the hidden one in this DB's `partner_names_order=first_last` configuration, leaving the actually-visible occurrence with no `readonly` attribute at all).
- Fixed by targeting both main occurrences explicitly (`[1]` and `[2]`) and changing the readonly condition for firstname and lastname from `read_only_user or is_tutor_readonly` to just `read_only_user`, so a tutor of the student can now edit both fields (previously they were locked out of the name entirely, alongside every other "non-contact field").

## Most "Student data" tab fields were locked for tutors:
- Everything under the student form's "Datos del estudiante"/"Student data" tab was read-only for a tutor (only admin/secretary could edit), even though tutors are the ones who actually notice and need to correct data-entry mistakes on their own students.
- Made editable for the tutor of the student: document ID (DNI/NIE), passport, medical ID, NUSS, car plate, birth date, birth country, citizenship, and special educational needs (NEE) - which now shows the editable dropdown for a tutor instead of a read-only badge.
- Kept locked to admin/secretary only, as requested: the student ID (IDALU), the student's own email address, and the already-computed "Adult" field.
- Added `TestContactTour._force_admin_language_to_english()` (same established pattern as `test_attendance_status_tour.py`) - the existing tour asserts on literal English tab names and was silently relying on the admin account's language, which isn't guaranteed to be `en_US` on every dev box; caught while re-verifying this tour against the changes above.

## "Email" was ambiguous with the student's institutional address:
- On a student's contact form, the generic "Email" field (the contact's own personal address, next to Phone/Mobile) looked interchangeable with `student_email` ("Student email", down in the "Student data" tab) - developer feedback: no clear signal which one is which.
- For `contact_type == 'student'` only: relabeled the generic field to "Personal email" (still editable, exact same underlying `email` field) and added a read-only "Corporate email" row right below it, mirroring `student_email` so it's visible without switching tabs. Every other contact type (family, applicant, provider...) keeps the plain "Email" field untouched.
- Implemented as two additional `<field name="email">`/`<field name="student_email">` instances with complementary `invisible="contact_type == 'student'"` / `!= 'student'` conditions (same duplicate-instance technique already used by `partner_firstname` for lastname ordering) - no change to the underlying fields themselves, existing read/write permissions on `email`/`student_email` still apply as before.
- New `string=` labels ("Personal email"/"Corporate email") translated in `i18n/ca_ES.po`/`i18n/es_ES.po` ("Correu personal"/"Correu corporatiu", "Correo personal"/"Correo corporativo"); "Personal email" reused an existing translation block (same English source text already used in `google_workspace_integration.py`), "Corporate email" is a new block. Verified against `ir_ui_view.arch_db` in the DB, not just the `.po` file, per the i18n verification rule in CLAUDE.md.
- Covered by a tour extension (`test_contact_tour.py`/`contact_tour.js`): opens a student with a `student_email` set and asserts both the relabeled row and the read-only mirror show the same address.

## "Car Plate" label assumed a car:
- `res.partner.car_plate` read "Placa de cotxe"/"Matrícula de coche" - developer feedback: the vehicle could just as well be a motorbike. Changed to "Matrícula del vehicle"/"Matrícula del vehículo" in `i18n/ca_ES.po`/`i18n/es_ES.po`. Verified against `ir_model_fields.field_description` in the DB.
